# Carfolio — Development Notes

A private, offline-first vehicle investment manager. One user, one device, no
server. This document is the reasoning behind the code: what the rules are, why
they are what they are, and where the traps sit.

---

## 1. Architecture

Five layers. The rule that shapes everything: **`domain/` imports nothing** — not
React, not SQLite, not Expo. Every dollar of arithmetic lives there, which is
what makes the money math testable in milliseconds and impossible to accidentally
couple to a screen.

```
app/          Screens and navigation (expo-router). No arithmetic.
state/        zustand: one snapshot of the database + UI filters.
services/     Files, PDF, backup. Split pure ↔ device in every case.
db/           Schema, migrations, repositories, transactional operations.
domain/       Money, dates, P&L, splits, capital, analytics. PURE.
```

Dependency direction is strictly downward. `domain/` is a leaf.

### The pure/device split

Three times during the build a test failed because pure logic was sitting in a
module that imported a native module. Each time the fix was to split the file,
and each time the result was better:

| Pure (testable in node) | Device-only |
|---|---|
| `services/reports/templates.ts` | `services/reports/render.ts` |
| `services/backup/bundle.ts` | `services/backup/files.ts` |
| `domain/postings.ts` | `db/operations.ts` |

The pattern: **decide what to write in a pure function; persist it in an impure
one.** `postingsForSale()` returns the rows a sale should create;
`recordSale()` writes them in a transaction. The sale screen calls the *same*
pure function to render its live preview, so the preview cannot disagree with
what gets saved.

### State

One `zustand` store holds a snapshot of the entire database, re-read after every
write (`withRefresh`). That sounds wasteful and is not — the whole dataset is a
few thousand rows — and it buys something worth far more than the millisecond:
every figure on every screen derives from one consistent view, so the dashboard
and a vehicle page can never disagree, and there is no cache to invalidate.

## 2. Data model

Conventions, applied without exception:

- **Money is `INTEGER` cents.** There is no `REAL` column in the schema.
- **Percentages are integer basis points** where they are stored at all.
- Business dates are `TEXT 'YYYY-MM-DD'` in **local** time.
- Audit timestamps are `TEXT` ISO-8601 **UTC**. These are different concepts and
  are never interchanged.
- Ids are generated by the app before a row is written, time-ordered.
- Every table has `created_at`, `updated_at`, `deleted_at`. **Nothing is ever
  hard-deleted.**

### Tables

| Table | Purpose |
|---|---|
| `vehicles` | The asset. Identity and spec — no money columns. |
| `expenses` | **The spine.** Every dollar spent on a car is a row here, including the purchase price. |
| `sales` | The closing event, with the split and allocation frozen at sale time. |
| `capital_events` | Contributions and withdrawals of principal. |
| `distributions` | Profit taken out by Daniel. |
| `fernando_entries` | One ledger: profit share, reimbursements, payments. |
| `inventory_items` / `inventory_usages` | Bulk supplies and draws onto vehicles. |
| `custom_categories` | User-added expense categories. |
| `photos`, `app_meta` | Attachments and key/value settings. |

### Two decisions worth knowing

**Purchase price is an expense, not a column.** It lives in `expenses` under the
`PURCHASE_PRICE` category, so there is exactly one place a dollar can live. Every
screen and report still presents it separately from additional investment — the
distinction is preserved in the *presentation*, not by duplicating the storage.
A `vehicle.purchase_price_cents` column would drift from the ledger the first
time an entry was corrected.

**No total is ever stored.** Total invested, gross profit, ROI and every average
are computed from rows on read. A stored total desynchronizes from its detail
eventually — always.

### Two constraints that do real work

```sql
CREATE UNIQUE INDEX uq_fernando_source ON fernando_entries (kind, source_id)
  WHERE source_id IS NOT NULL AND deleted_at IS NULL;
```

An expense Fernando paid can produce exactly **one** reimbursement; a sale
exactly one profit share. A double-tapped save button or a retried write cannot
create a second — the insert fails. The specification asks that the same
reimbursement never be counted twice; this makes it structurally impossible
rather than a rule someone has to remember. (`operations.test.ts` proves it by
attempting the duplicate insert directly.)

```sql
CREATE UNIQUE INDEX uq_sales_active_vehicle ON sales (vehicle_id)
  WHERE deleted_at IS NULL;
```

One *live* sale per vehicle. A reversed sale is soft-deleted, so the car can be
sold again — but two active sales for one car is not representable.

## 3. Financial rules

### Vehicle types

- **MYSELF** — Daniel works it alone. 100% of profit or loss is his.
- **ASSOCIATED** — worked with Fernando. Profit and loss split 50/50.

Daniel funds 100% of the capital in both cases. Fernando contributes labour, not
money — except when he pays an expense out of pocket, which is a reimbursable
debt rather than a capital contribution.

### Allocation applies to Daniel's share only

This is the most important rule in the app.

On a $3,000 ASSOCIATED profit, Fernando's $1,500 is **his the moment the car
sells**. It posts straight to his balance. The reinvest/distribute decision then
applies only to Daniel's $1,500.

You do not get to reinvest someone else's money, and the sale screen is built so
that "reinvest Fernando's half" is not expressible: the allocation control is
bounded by `danielShareCents`. `validateAllocation()` rejects anything that
doesn't sum to exactly that figure.

### Losses

The same 50/50 rule applies. Fernando's negative share posts to his balance and
**carries forward against his future profit** — no cash changes hands over a
loss. His balance can legitimately be negative.

On a losing sale there is nothing to allocate; the negative share simply reduces
retained earnings.

### The odd cent

$3,000.01 cannot be halved evenly. By convention the extra cent goes to Daniel —
he carries the capital risk — and the same rule applies to losses, so he also
absorbs the extra cent of a loss. `first + second === total` always holds, and a
property test asserts it across the full integer range.

### Protected capital

Four quantities are kept strictly apart:

| | Changed by | NOT changed by |
|---|---|---|
| **Protected capital** | capital contributions / withdrawals | profit, distributions, reinvestment |
| **Retained earnings** | Daniel's realized shares, distributions | capital events |
| **Owed to Fernando** | his shares, his out-of-pocket expenses, payments to him | anything else |
| **Cash on hand** | every actual movement of money | nothing else |

Selling a car at a profit does **not** increase protected capital. Taking a
distribution does **not** reduce it. The UI reinforces this: the principal sits
in its own bordered gold panel on both the dashboard and the Capital screen,
with an explicit statement that nothing else on the screen can move it.

## 4. Calculation formulas

```
purchasePrice        = Σ expenses where category = PURCHASE_PRICE
additionalInvestment = Σ expenses where category ≠ PURCHASE_PRICE
totalInvested        = purchasePrice + additionalInvestment

grossProfit          = salePrice − totalInvested
roi                  = grossProfit ÷ totalInvested        (null if invested ≤ 0)
daysHeld             = saleDate − purchaseDate            (today − purchase, if unsold)

MYSELF:      daniel = grossProfit                fernando = 0
ASSOCIATED:  fernando = trunc(grossProfit / 2)   daniel = grossProfit − fernando

reinvest + distribute = max(0, danielShare)
```

`paidBy` never affects a vehicle's cost. If Fernando bought the tires, the tires
are still $500 of investment in the car — who fronted the money is a question
about *his balance*, not about what the car cost. Keeping those two questions
separate is what stops the reimbursement being counted twice.

### Business position

```
protectedCapital  = Σ contributions − Σ withdrawals
capitalDeployed   = Σ totalInvested of UNSOLD vehicles
capitalReturned   = Σ totalInvested of SOLD vehicles
retainedEarnings  = Σ danielShare(sold) − Σ distributions
owedToFernando    = Σ fernando entries (signed)
inventoryValue    = Σ lot purchase cost − Σ inventory draws

cash = protectedCapital
     + Σ salePrice
     − Σ expenses where paidBy ≠ FERNANDO and not fromInventory
     − Σ distributions
     − Σ payments to Fernando
     − Σ inventory lot purchases
```

Two exclusions in the cash line carry the whole double-counting guarantee:

- an expense **Fernando paid** never leaves Daniel's cash — it becomes a
  liability, and only the `PAYMENT` entry moves cash;
- an expense **drawn from inventory** never leaves cash either — the cash left
  when the stock was bought.

Miss either and the same dollar is spent twice.

### The accounting identity

```
cash + capitalDeployed + inventoryAtCost
    ===  protectedCapital + retainedEarnings + owedToFernando
```

This holds after every possible sequence of operations. `verifyIdentity()`
checks it; **Settings → Data integrity** shows it to the user rather than hiding
it, because a number that silently stops adding up is far worse than one that
visibly complains.

### Two ROIs, deliberately

Analytics reports both, labelled differently:

- **Average ROI per vehicle** — the mean of each car's own return.
- **Return on money invested** — total profit ÷ total invested.

They differ when deals are different sizes. A $200 profit on a $400 car and a
$1,000 profit on a $20,000 car average **27.5% per car** but returned **5.9% on
the money**. Reporting only the first is how these screens flatter people.

### ROI is null, never Infinity

When nothing was invested, `roi()` returns `null` and the UI renders an em-dash.
A screen that prints `Infinity%` has lost the user's trust for every other number
on it.

## 5. Storage strategy

**SQLite via `expo-sqlite`, with Drizzle** for a typed schema and generated
migration files.

Not AsyncStorage: the reference project rewrote its entire dataset as one JSON
string on every mutation, and Android's AsyncStorage ships with a ~6 MB ceiling.
A ledger outgrows that in the first year.

Two pragmas are set on every open, because SQLite does not remember them:

```
PRAGMA journal_mode = WAL;   -- survives the app being killed mid-write
PRAGMA foreign_keys = ON;    -- enforcement is OFF by default
```

### Migrations

Generated by `drizzle-kit` into `drizzle/`, checked in, never hand-edited. The
same generated files are applied by the app (`expo-sqlite`) and by the test
suite (`better-sqlite3`), so **migrations are exercised on every CI run** rather
than first discovered on the phone — where a failure means an app that will not
open and no cloud copy to restore from.

The boot sequence surfaces migration state and, on failure, shows a real screen
pointing at Backup & Restore rather than an endless spinner.

### Deterministic ordering

Every ordered query carries `id` as a final tie-break. Without it, rows sharing a
date come back in whatever order SQLite happens to produce — lists would
reshuffle between refreshes and an exported backup would not round-trip to an
identical snapshot. (This was found by the round-trip test, not by inspection.)

### Backup

- Schema-versioned JSON bundle. **Human-readable**, not an opaque dump: if
  Carfolio ever stops working, the history is still legible in a text editor.
- A bundle from a **newer** version is refused outright — half-reading it would
  silently drop whatever it added.
- Import **validates completely before writing anything**, takes an automatic
  pre-import snapshot, and restores inside one transaction. A failed restore
  rolls back entirely.
- Import **replaces, never merges.** Merging two divergent copies of a financial
  history is a conflict-resolution project, and a wrong merge is worse than no
  merge — it produces a plausible set of wrong numbers.
- The app nags when the last export is more than 14 days old. This is not a
  dismissible nicety: it is the only thing standing between the user and total
  loss.

## 6. PDF strategy

`expo-print` renders HTML; `expo-sharing` hands the file off.

Templates are **pure functions from data to an HTML string** in
`services/reports/templates.ts`. Nothing there touches the device, so reports are
snapshot-tested in plain node — a broken report is caught in CI rather than after
it has been sent to Fernando.

Design is deliberately conservative: black on white, real typographic hierarchy,
tabular figures. It will be read on someone else's phone, forwarded, and possibly
printed. **No colour carries meaning** — a loss is labelled "Gross loss", not
merely printed in red.

Two reports:

- **Vehicle report** — one car in full. Complete investment breakdown, the sale,
  the profit, how it was split, Fernando's entries for that car. On an ASSOCIATED
  vehicle it explains that Fernando's share is computed on gross profit and is
  his in full at the point of sale, so it stands on its own as a document.
- **Business summary** — capital position, YTD split by Myself/Associated,
  Fernando's running balance, all-time performance, full vehicle history.

Every report is stamped with its generation date. Editing a record afterwards
changes the app but not a PDF already sent, so an issued report is a snapshot.

User text is HTML-escaped — a note containing `<script>` cannot break the
document.

## 7. Testing strategy

```
210 tests · 13 suites · ~3s
domain/ coverage: 98.7% statements · 92.3% branches
```

**Running them needs one extra step:** `npm run test:setup`.

`better-sqlite3` is deliberately NOT in `devDependencies`. It is an *optional
peer dependency of `drizzle-orm`*, which means npm auto-installs it and marks it
as a non-dev package — so `npm install --omit=dev` does not skip it. It is a
native module, so on a machine without a C++ toolchain the plain `npm install`
fails outright and the app cannot be run at all.

That is a real trap and it cost a user a working install. Requiring Visual Studio
Build Tools to open a car-flipping app is not a trade worth making, so the driver
is opt-in for whoever runs the tests.

Weighted hard toward the bottom of the pyramid, for a specific reason: in this
app the expensive bugs are not crashes, they are **wrong numbers that look
right**. A screen that fails to render is noticed in seconds. A split that is off
by a rounding cent is noticed in a conversation with Fernando six months later.

| Layer | Tool | What it covers |
|---|---|---|
| Domain unit | Jest, plain node | money, dates, P&L, splits, capital, analytics |
| Property-based | fast-check | invariants across randomized histories |
| Integration | Jest + better-sqlite3 | real SQL, real migrations, real transactions |
| Round-trip | Jest | export → wipe → import → deep equal |
| Report snapshot | Jest snapshots | full HTML output for fixture deals |
| Navigation | Jest | every route referenced actually exists |
| Static | tsc strict · ESLint | types, style, banned patterns |

### The three that matter most

1. **The accounting identity, property-tested.** 400 randomized sequences of
   buy / expense / sell / stock / draw / pay-Fernando, asserting the identity
   after every one. It catches an entire class of bug nobody has to imagine in
   advance. The scenarios are built with `domain/postings.ts` — the same
   functions the app writes through — so it validates the real write-rules
   rather than a reimplementation that could drift.

2. **Backup round-trip.** Export a populated database, wipe it, import, assert
   every table deep-equals the original. With no server, this is the only thing
   standing between the user and silent total loss. It includes an odd-cent
   associated split, a Fernando-paid expense, an inventory draw, and a full
   JSON serialization pass — not just an in-memory copy.

3. **Migration chain.** The tests run the same generated migrations the phone
   runs. Break these and the app will not open after an update.

### Custom lint rules

Two greps in CI worth more than a lot of tests:

```js
'no-restricted-globals': parseFloat        // money is integer cents
'no-restricted-syntax':  .toFixed()        // rounding bug on money
'no-restricted-syntax':  .toISOString()    // UTC shifts business dates
```

They fired on the first run and caught three real spots — all inside the modules
that *implement* the safe versions. Those carry documented exemptions; the ban
stays live everywhere else so the mistake cannot spread.

### Accessibility finding

The `dataviz` palette validator reports profit-green `#6EE7C8` against loss-red
`#F2748F` at **ΔE 7.1 under deuteranopia** — the classic red/green failure and
the most common accessibility bug in financial interfaces. Colour is therefore
never allowed to carry meaning alone:

- the chart uses a **zero baseline** (bars up/down encode sign by position);
- every signed figure prints an explicit **`+` or `−`**;
- losses are **labelled** "Gross loss", not merely coloured.

A red/green-blind reader loses nothing.

### What is NOT covered

Rendering on a real device. The container this was built in cannot run a
simulator, so screens are verified by typecheck, lint, and the route test — not
by pixels. Run `npx expo start` and walk the flows before trusting the UI.

## 9. Future improvements

Ordered by value, not effort.

1. **Photos.** The `photos` table and the schema are in place; the picker,
   downscaling (to ~1600px) and the gallery are not. Downscale on import or forty
   vehicles of camera-resolution photos will fill the phone.
2. **Automatic local backup ring.** Currently backup is manual. A rotating set of
   on-disk snapshots plus weekly anchors — never snapshotting an empty state —
   would add a safety net beneath the manual export.
3. **CSV export for an accountant.** Ten lines of code, saves a weekend every
   April. Every ledger entry for a year, with categories.
4. **Biometric lock.** `expo-local-authentication` with a PIN fallback. Purchase
   prices and profit figures on a phone that gets handed around.
5. **A max-bid calculator.** Target value − estimated recon − expected selling
   costs − required margin = the number not to exceed at auction. The only
   forward-looking feature the app could have; everything else is record-keeping
   about decisions already made.
6. **Estimate vs. actual recon variance.** Store the pre-purchase estimate,
   compare to actual. After ten cars you know your own bias.
7. **Title and paperwork tracking.** Title status, in-hand flag, temp tag expiry.
   Paperwork stalls more flips than mechanics do.
8. **Bilingual UI.** All user-facing strings are inline today. Routing them
   through a string table makes Spanish a drop-in rather than a refactor.
9. **Cloud sync, if it is ever wanted.** Every table already has `updated_at` and
   soft deletes — the two decisions that separate "add sync in a week" from
   "rewrite the data layer". Repositories are behind a single `Db` type.
10. **Maestro E2E flows.** 4–6 smoke journeys on a real build: add → expense →
    sell → verify P&L; export → import; associated split → settle.

## 10. Decisions made without being asked

Each is cheap to reverse; each is written down rather than assumed.

1. SQLite + Drizzle over AsyncStorage.
2. Purchase price stored as an expense, presented separately everywhere.
3. Integer cents throughout; no floats touch money.
4. Soft deletes and `updated_at` on every table.
5. `SOLD` cannot be set as a status — only `recordSale()` writes it, in the same
   transaction as the sale row, so a vehicle can never appear sold without a sale.
6. A sale is reversed, never deleted.
7. Import replaces rather than merges.
8. Inventory is valued as lot cost minus draws, not `quantity × unitCost` —
   multiplying back out rounds independently on each side and drifts a cent or
   two away from what actually left the bank, which would break the identity.
9. The last draw from a lot takes its entire remaining value, so an emptied lot
   leaves no phantom cent on the books.
10. The odd cent of any split goes to Daniel, in both directions.
11. Custom categories are archived, never deleted — expenses store the id.
12. Analytics averages cover sold vehicles only.
13. English identifiers in code; UI strings inline pending i18n.
14. Data integrity is surfaced to the user rather than hidden.

## 11. SDK version

Built and verified on **Expo SDK 57** (React Native 0.86, React 19.2).

iOS Expo Go only ever supports the newest SDK — you cannot install an older
build of it — so the project must track whatever SDK the installed Expo Go
expects. To move it forward later:

```bash
npm install expo@<new version>
node -e "console.log(require('./node_modules/expo/bundledNativeModules.json'))"
# install every listed package at its pinned version, then:
#   update "sdkVersion" in app.json
npm run typecheck && npm run lint
```

An earlier SDK 54 build of this project failed at the Hermes bytecode step on
React Native's own `DOMRectReadOnly` polyfill. SDK 57 exports cleanly
(`npx expo export --platform ios`, 1,300+ modules, migrations inlined), so that
issue is resolved and the note describing it has been removed.

## 12. The selector trap (fixed, and now tested)

The app crashed on first launch with *Maximum update depth exceeded*.

zustand reads through `useSyncExternalStore`, which compares what a selector
returns **by identity**. A selector like

```ts
useApp((s) => s.vehicles.filter((v) => !v.financials.sold).sort(...))
```

builds a brand-new array on every call, so React sees a changed value on every
render and loops until it bails out. The logic was correct; the identities were
not — which is why typecheck, lint and 202 passing tests all missed it.

**The rule now:** a selector is a *field read*, never a computation. Every sorted
or filtered view is computed once per refresh inside `derive()` and stored, so
its identity only changes when the data does. Where a screen needs a narrower
slice, it selects a stable field and narrows it in a `useMemo`.

`__tests__/services/selectors.test.ts` asserts referential stability directly,
and was verified to fail when the old pattern is reintroduced — the check has
teeth, not just green ticks.

## 13. The web build — installable on the phone

Carfolio also builds as an installed web app, which is how it runs on an iPhone
without a developer account: `npm run build:web`, drop `dist/` on any static
host, then Share → Add to Home Screen in Safari.

It is the same app, not a cut-down version. What differs, and where:

| Concern | Native | Web |
| --- | --- | --- |
| SQLite | expo-sqlite (a file) | sql.js — SQLite compiled to WebAssembly |
| Storage | the file is the storage | the database is serialised to IndexedDB after every write |
| Migrations | drizzle's expo-sqlite migrator | the same SQL, emitted by `npm run db:web` |
| PDF | expo-print | the browser's own print-to-PDF |
| Backup | share sheet | a download, which iOS routes to Files |
| Offline | inherent | a service worker caching the whole bundle |

Every one of those lives behind a `.web.ts` file that Metro picks automatically.
No screen, repository, operation or domain function branches on platform, and
`domain/` does not know a browser exists.

**The one honest caveat.** Browser storage is not the same promise as an app's
container: deleting the home-screen icon deletes the data, and it is not in the
device's iCloud backup. `navigator.storage.persist()` is requested at boot,
which an installed web app is granted, but the real protection is Backup &
Restore — which is why the app pushes it after a sale.

**Why sql.js rather than an IndexedDB object store.** Re-implementing the
queries against IndexedDB would have meant two versions of every read and two
places for the money arithmetic to disagree. Running actual SQLite in
WebAssembly costs ~650KB once and keeps a single source of truth for the
schema, the constraints and the sums.

### Verified, not assumed

The web build was driven in a real headless browser before shipping: boot with
no console errors, a capital contribution written through the UI, the browser
process closed entirely, reopened against the same profile with the $30,000
still there, and finally the whole app opened again with the network switched
off.

### Known compromise

The tab bar shows icons only on web. react-navigation's web tab bar collapses
its label box to a 1px sliver regardless of the style it is given; clipped text
is worse than no text, so labels are native-only. Worth revisiting when the
library fixes its web label layout.

### What driving the web build in a real browser found

Three defects that no unit test could have caught, because each was about the
platform rather than the logic:

1. **`Alert` does not exist on the web.** `Alert.alert` with buttons is a silent
   no-op in react-native-web, so "Restore from a backup?" never appeared and the
   restore path was completely dead in the installed app — the one path the
   whole safety story depends on. Every error message the app tried to show was
   swallowed too. Dialogs now go through `components/ui/dialog.ts`, which the
   web build swaps for `window.confirm` / `window.alert`.

2. **The restore confirmation consumed the user gesture.** A file input only
   opens while a gesture is live, and a dialog in front of it eats that gesture.
   The flow is now pick → validate → confirm → apply: the picker opens on the
   tap itself, and the confirmation appears afterwards, naming what is actually
   in the chosen file. Better on both platforms, not just a workaround.

3. **The last-backup date lived in memory only.** It was set in the store but
   never written to the database, so the app forgot every backup on the next
   launch and insisted none had ever been taken. It now goes through
   `withRefresh`, which is also what flushes it to storage.

The safe-area insets are handled by the page's own `env(safe-area-inset-*)`
padding rather than inside React, because react-native-safe-area-context reports
zero on web and the first line of every screen would otherwise sit behind the
iPhone's clock.

`__tests__` cannot drive a browser, so these paths are covered by scripts run
against a real Chromium: the full business flow (capital → purchase → expense →
sale → integrity → restart), the backup loop (export → restart → prompt clears),
the restore (fresh profile → import → figures and books come back), every screen
for console errors, and the PDF report's document actually being built.

### The backup prompt

`domain/backupStatus.ts` decides when the dashboard asks for a backup. It is
driven by work done rather than the calendar alone — nagging on a timer teaches
people to ignore it, asking after a sale does not. It stays silent on an empty
app, silent for a record or two, suggests after a week or five records, and
turns overdue at a month or when no backup has ever been taken.
